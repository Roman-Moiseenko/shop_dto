# Шаблон API CRM Интернет магазина на чистой архитектуре

## Общее. 
### Доступы
Доступ определяется ролями. Базовые роли, которые разграничивают маршруты - admin, staff, client
Каждый модуль содержит системные роли разделенные по сущностям (возможно пересечение, объединение)
Например доступы для работы с клиентом (без учета доступа к User) создаем роль buyer с доступами:
 - auth.buyer.create,
 - auth.buyer.edit,
 - auth.buyer.view,
 - auth.buyer.delete,
 - auth.buyer.force,
 - auth.buyer.blocked.

Системные роли создаются через Seeder в каждом модуле.
Пользовательские роли создаются из доступов и назначаются сотрудникам. Системные роли не могут быть назначены.
### Обработка исключений
Исключения модулей обрабатываются в своих провайдерах, см. на примере **AuthServiceProvider**

### DTO и Валидация
Для DTO и Валидации используем Spatie\Laravel\Data
- {Entity}Data - универсальный DTO для создания и изменения, с валидацией
- {Entity}CreateData - DTO для создания с валидацией
- {Entity}UpdateData - DTO для редактирования с валидацией
- {Entity}IndexData - DTO для списков при получении данных через Index{Entity}UseCase без валидации. Обязательное поле **id**
- {Entity}ViewData - DTO для полных данных сущности при получении данных через View{Entity}UseCase без валидации. Обязательное поле **id**
- {Entity}OptionData - DTO для списков в компонент **\<select />** без валидации, два параметра id(:key) и name(:label)

Во всех {Entity}ViewData необходим метод **public static function fromEntity({Entity}Entity $entity): self**, который мапает закрытые поля в объект
Во всех {Entity}IndexData необходимо переопределить метод from для использования коллекции

>Возможно использование одного DTO {Entity}ViewData если сущность содержит мало полей и кол-во в таблице совпадает со всем кол-вом полей 


```
public static function from(mixed ...$payloads): static
{
    if (count($payloads) === 1 && $payloads[0] instanceof {Entity}Entity) {
        return static::fromEntity($payloads[0]);
    }

    return parent::from(...$payloads);
}
```

### Интерфейсы
- MailServiceInterface - почтовый интерфейс, для отправки почты. При монолите прописан будет в модуле почты, при микросервисах отправка будет через очереди в Shared

## Модуль Auth
Модуль аутентификации и настройки доступа.

### Сущность User
 Сущность аутентификации. Может быть только в связке с сущностями пользователя.
 Кроме admin созданного через Консольную команду

 Все сущности могут иметь доступ к программе (иметь связанный User) или не иметь,
но User не может быть создан отдельно, через api.

### Сущность Staff
Сущность сотрудника, может не иметь доступа к программе, например логисты, которые учитываются в табелях и/или
могут иметь доступ к корпоративному боту для получения задач. 
При установке доступа, назначаются роли.
### Сущность Client
Клиента можно создать без доступа, через запрос из других модулей, например обработка Лидов и/или Заказов.
Если клиент регистрируется самостоятельно через форму на сайте, то создается помимо сущности Client, 
привязанный к нему User с ролью 'client'
### Сущность Freelance
Сущность с минимальными данными, для внештатных сотрудников. Роли назначаются отдельно для каждого.
Специальной роли для Freelance не предназначено

## Модуль Storage
### Сущность Media
Единая сущность для хранения изображений всех остальных сущностей CRM.

- MediaController – для менеджеров и публичного показа.
- ClientMediaController – только для клиентов.
#### Базовые типы для хранения MediaType
 - icon
 - image
 - gallery - множественное хранение

Для единичного хранения типа image - каждая загрузка замещает предыдущую, для множественного - добавляет в список
Оригиналы хранятся в локальном хранилище, к ним есть доступ через получение бинарных данных для менеджеров, во всех остальных случаях идет работа с копиями.
При загрузке изображения:
- генерируется новое уникальное имя для файла
- оригинал с новым именем копируется в локальное хранилище
- создается копия с таким же именем в публичном хранилище, при необходимости изображение квадрируется и устанавливается водяной знак
- создаются по настройкам обрезанные копии (нарезка)

Кеш можно полностью очистить, и при первом обращении к изображению, все копии пересоздадутся заново.

### Сущность Tag
Метки для медиа, используется для фильтрации изображений в Галереях

### Сущность Gallery
Сгруппированные наборы изображений для многократного использования в сущностях, которые имеют поле mediaUuid. Например, пункты меню, иконка для каталога, изображения для виджетов 

## Модуль Content
Модуль клиентской части сайта, содержит статичные страницы, блог, меню, виджеты для управления контентом и другое

## Сущность Page
Сущность страницы на сайте, стандартный компонент, имеет возможность отображать как свой контент (text), так и состоять из блоков (виджетов)

## Сущности Widget
Три сущности - настройка виджета, наполнение виджета (экземпляр настройки) и связующий блок для Page и Post
Таблицы
1. widgets — Типы виджетов. Хранит системные шаблоны виджетов, которые определяют их возможности и параметры настройки.
2. widget_instances - Экземпляры виджетов. Хранит конкретные настроенные экземпляры, готовые для размещения на страницах. Один тип виджета может иметь множество экземпляров с разными настройками.
3. content_blocks - Связующая таблица. Определяет, в каком контейнере (страница или запись блога) и в каком порядке (sort_order) размещается конкретный экземпляр виджета

Принцип
 1. Создание нового типа виджета (Widget)
   
Системный администратор через API добавляет запись в таблицу widgets. Он указывает name, slug и самое главное — schema в формате JSON Schema. Эта схема служит "контрактом" для будущих экземпляров

```
slug: "text_block"
category: "content"
schema:  
    {
        "type": "object",
        "properties": {
            "content": { "type": "string", "title": "Текст" },
            "text_align": { "type": "string", "enum": ["left", "center", "right"], "default": "left" }
        }
    }
```

2. Создание и настройка экземпляра виджета (WidgetInstance)

Менеджер в админке выбирает тип виджета (widget_id), и интерфейс на основе его schema динамически генерирует форму. Менеджер заполняет параметры, и создаётся запись в widget_instances, где params содержит уже конкретные значения.
```
widget_id: 1 (ссылается на text_block)
uuid: a1b2c3d4...
params:
{
    "content": "<p>Наша компания является лидером...</p>",
    "text_align": "center"
}
```
3. Размещение виджета на странице (ContentBlock)

   Чтобы добавить созданный экземпляр виджета на страницу, менеджер переходит в редактор страницы (с типом контента widget_based). Он выбирает один из готовых экземпляров виджетов и указывает его позицию (sort_order). Так создаётся запись в таблице content_blocks, связывающая page (через container_type и container_id) с widget_instance_id.
